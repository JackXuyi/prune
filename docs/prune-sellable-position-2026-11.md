# Prune 的下一个可售位置（2026-11）

> 版本 v1.0 ｜ 2026-11-16 ｜ 基线 v0.11.0
> 输入：`README.md` / `README.zh-CN.md`（v0.11.0 承诺面）、`docs/prune-requirement-insight-2026-11.md`（商业化结论）、`docs/prune-roadmap-2027-dev-first.md`（M0′–D-17 路线）、`crates/prune-cli/src/mcp.rs`（工具面代码级核验）
> 标注约定：**【事实】**可追到文件/代码 ｜ **【估算】**有依据未验证 ｜ **【假设】**需数据校准
> 本文件只回答一个问题：**在不改三条底线的前提下，Prune 的钱可能从哪来。** 不重证产品价值，不重排路线图优先级。

---

## 0. 一句话结论

**Prune 卖不出"清理"，但能卖出"一份别人无法反驳的机器体检"。**

下一个可售位置不在 C 端，而在"需要这份证据去做决策的人"手里：

> 把体检从「产品内部的一个 tab」变成「可以对外出具的凭证」，先卖给**卖开发环境的人**（云开发机 / 远程开发 / AI IDE），再由这份信誉承接**管着几十台开发机的团队**（白名单维护订阅）。

两条位置共享同一个动作：**不加探测能力，只改交付身份。**

## 1. 为什么 C 端没有位置（结构证明，不是悲观）

三条底线不是营销口径，是三条商业约束。它们各自废掉一种定价能力：

| 底线 | 【事实】出处 | 被废掉的商业机制 |
|---|---|---|
| MIT 许可 | `LICENSE` | **功能 gate**——没有"付费版才有"的东西，任何二进制都能自建 |
| 零遥测 | README「Agents read, humans delete」 | **按量计费**（不知道谁用了多少）、**留存验证**（无法判断续费依据） |
| 无账号 | README「no account」 | **席位订阅**（无法验证谁在用、无法吊销、无法开票到人） |

三者叠加后的唯一可行形态是**一次性买断**；而买断要求"每年 110–210 单新增销售，且必须每年重复"（`prune-requirement-insight-2026-11.md` §①）。单人渠道 + 零广告预算做不到。

**结论不是"暂不商业化"（时间问题），是"这个位置上不存在商业模型"（结构问题）。** 所以"找下一个位置"不是往前走一步，是换一个坐标系。

## 2. 五个候选位置与评判

评分 1–5，全部为【判断】（依据见各位置说明）。

| # | 位置 | 买家 | 记在哪个科目 | 可归因 | 底线兼容 | 单人可交付 | 用既有资产 | 竞争空隙 | 合计 | 判定 |
|---|---|---|---|---|---|---|---|---|---|---|
| **P-A** | **体检 OEM**（把报告/读数层嵌入别人的售前与产品） | 云开发机 / AI IDE / MDM / 构建缓存厂商 | 市场获客 + 产品集成 | 5 | 5 | 3 | 4 | 4 | **21** | **推荐** |
| **P-B** | **白名单维护订阅**（卖责任，不卖功能） | 有 50+ 开发机的团队 | IT 运维 / 工具预算 | 4 | 4 | 4 | 5 | 3 | 20 | **备选（P-A 之后）** |
| P-C | 容量决策报告（一次性咨询式） | IT / 财务（硬件预算） | 硬件采购 | 5 | 5 | 2 | 4 | 4 | 20 | 不做（无法规模化，是卖时间） |
| P-D | Agent 运行时读数插件 | Agent 平台 | 研发工具 | 3 | 5 | 3 | 5 | 2 | 18 | 不做（见 §5） |
| P-E | 事故现场取证包 | on-call / SRE 团队 | 事故成本 | 3 | 4 | 2 | 3 | 1 | 13 | 不做（红海 + 根因不在本机） |

P-C 总分与 P-B 并列，但它是"卖自己的工时"（每单都要人做），与"单人 3 人日/周"的产能口径直接冲突，因此排除——**总分相同不等于可选项相同，产能是硬约束。**

## 3. 推荐位置 P-A：卖「可信体检」给卖开发环境的人

### 3.1 卖的是什么（一句话，对外可用）

> **给卖开发环境的人，一把能当场量出"你这台机器已经不够用了"的尺子。**

不是工具，是证据；不是给开发者，是给他们的**售前环节**。

### 3.2 谁付钱、为什么付

| 买家类型 | 他们的销售环节缺什么 | Prune 正好有什么 |【判断】付费动机 |
|---|---|---|---|
| 云开发机 / 远程开发（Coder、Gitpod、Daytona 一类） | 一个"你本机已经撑不住"的当场证据，而不是一句"上云更爽" | 可回收 GB、重复存储比、swap 占满率、换出受害者 | **强**——这是他们获客漏斗的第一环 |
| AI IDE / Agent 产品 | Agent 不知道自己跑在什么机器上（内存压力、端口占用、依赖体积） | 12 个只读 MCP 工具【事实】 | 中——但他们会倾向自建 |
| Mac 管理 / MDM（Jamf、Kandji 一类） | 开发机侧的"浪费与容量"信号，别处拿不到 | 68 条白名单 + 分级 + 护栏 | 中——采购链长 |
| 包管理 / 构建缓存厂商 | "同一个依赖你存了三份、29 GB"这种可传播的数字 | npm/Yarn/pnpm 重复存储归因 | 中——更像联合营销而非采购 |

**付钱的三条真实理由**（不是"我们的产品很好"）：

1. **他们自建的成本被低估了。** `phys_footprint` 要调 `/usr/bin/footprint` 并解析 swap 分项；端口归属要处理 `lsof` 无权限时的 coverage；白名单要 68 条带断言测试。让一个销售驱动的团队自己维护这套口径，比买一份 MIT 可审计的实现贵。
2. **可审计性本身就是卖点。** MIT + 零遥测 + 无账号，意味着他们可以把这份体检结果直接放到客户面前，而不会被质疑"你们在自己收集数据"。这是**采购阻力最低的一种技术选型**。
3. **它把"感觉慢"变成"可复核的数字"。** 这与 Prune 已有的产品纪律完全同源（0 与"读不到"不同、怀疑不下判决）。

### 3.3 定价形态（三档，全部【估算】，成交前不得对外引用）

| 形态 | 交付内容 | 价格区间【估算】 | 等价于多少单 $29 |
|---|---|---|---|
| 联合品牌体检（co-branded build + 落地页） | 一份带他们品牌的报告入口，口径与护栏归 Prune | 一次性 $3–8k + 年维护 $2–5k | 100–280 单 |
| 读数层集成（12 个 MCP 工具作为"本机上下文"） | 契约冻结 + 集成支持 + 版本跟随承诺 | 年授权 $10–30k | 340–1000 单 |
| 口径背书（"缓存路径由 Prune 维护"） | 白名单维护 + 变更通告 + 联合发布 | $5k/年 | 170 单 |

**读法**：一单顶一百到一千单。这不是"更赚钱的定价"，是"唯一的定价"——因为 C 端的量在单人渠道里不存在。

### 3.4 交付物（不新增任何探测能力）

| 交付物 | 现状 | 缺口 |
|---|---|---|
| `prune report --md --json`：一份带时点、口径、不可读项原因、可复核证据的体检报告 | **不存在**（JSON 部分覆盖，无统一报告） | 需新增，路线图 D-14 已有设计 |
| 口径说明（为什么 `phys_footprint` 而不是 RSS；为什么 0 ≠ 读不到） | 散落在 README | 需抽成独立一页，可对外 |
| co-brand 入口（一个 URL / 一个二进制） | 无 | 商务决定后才有 |

### 3.5 需要的最小新增能力：3 项，全部已在路线图里

| 需要 | 路线图位置 | 为什么是前置 |
|---|---|---|
| D-01 签名 + 公证 | Wave 1 | 给企业交付一个"已损坏，无法打开"的二进制，报价会被当场终止 |
| D-03 契约 v1（`schemaVersion` + 退出码表） | Wave 1 | OEM 买的是**稳定接口**，不是功能 |
| D-14 报告导出 | **Wave 3 → 提前到 Wave 1** | 没有可出具的凭证，就没有可报价的商品 |

**结论：商业化不改变路线图，只改一条顺序。** 其余 D-02/D-04/D-05 一律不动。

## 4. 备选位置 P-B：卖「责任」，不卖「功能」

**买家**：有 50+ 开发机的团队（平台工程 / IT）。
**年费**：$500–3,000【估算】。
**买的是四件事**，全部与代码无关：

| 买的东西 | 为什么 MIT 下仍然可卖 |
|---|---|
| 缓存路径的及时更新（AI CLI 目录每月都在变） | fork 可以拿走代码，拿不走"谁在维护" |
| 误删兜底的响应承诺 | 卖的是时间与责任，不是许可 |
| 发票、采购材料、安全问卷答复 | 大公司采购流程的硬需求，开源项目天然缺失 |
| 版本节奏的确定性（谁保证下季还有更新） | 这是"可持续性保险"，不是功能 |

**必须守住的两条**：不承诺 24h SLA（单人做不到，写进去就是负债）；不卖"私有白名单"（会破坏白名单的单一事实源）。
**前置**：需要 P-A 带来的至少 3 个公开案例与一份可出示的报告，否则没有谈判资格。

## 5. 明确不做的四个位置

| 位置 | 不做的理由 | 若强行做的代价 |
|---|---|---|
| 个人订阅（$3–5/月） | MIT + 无 gate，付费者与免费者拿到同一个二进制 | 等于向自己的用户收"自愿捐赠"，且需解释为什么不给功能 |
| 团队看板 SaaS | 直接违反零遥测 + 无账号两条底线 | 一旦破例，README 全部承诺失效，且单人无法承担运维与合规 |
| AI 清理建议（付费） | "几乎对"的删除建议在本场景 = 资损，不是体验问题 | 用唯一资产（可信）换一个 60% 已被免费工具占据的功能 |
| Agent 读数插件（P-D） | Agent 自己跑 `df` / `ps` 就能拿到大部分读数，**自建成本≈0** | 只剩"口径正确性"一条窄护城河，且买家会先自建再考虑买 |

> P-D 的残余价值：作为 P-A 的一个**集成形态**存在（第三个定价档），不单独立项。

## 7. 90 天验证计划（0 工程日 + 8 运营日）

目标：**用最小成本证伪 P-A**，而不是证明它是对的。

| 周 | 动作 | 产出 |
|---|---|---|
| W1–2 | ~~不写代码，手工拼一份样例体检报告~~ → **改为脚本自动化**（见 `w1-report-sample-plan.md`；doctor/契约 v1 已落地，脚本 3.5 工程人日 + 60s/份，替代每次手工 1–2 天） | 一份可直接发给买家的 PDF/MD |
| W3–4 | 列 20 个目标买家（云开发机 6 / AI IDE 5 / MDM 4 / 构建缓存 5），发 20 封三句话邮件 | 20 封发出记录 |
| W5–8 | 做 3 次 30 分钟对话，只问三个问题 | 对话记录 |
| W9–12 | 争取 1 份 LOI 或 1 笔任意金额的付费试点 | 合同或转账凭证 |

**对话三问**（不要问"你觉得有用吗"，那必然得到礼貌的假话）：

1. 你们现在怎么向客户证明"他本机已经不够用了"？谁写这份材料？
2. 如果自己写，需要多久、谁维护？（这条直接测 §3.2 第 1 条理由）
3. 这份体检如果由第三方出具并带你们的品牌，你们愿意为什么付费——集成、维护，还是一次性？

**判据（不达标即停，不解释、不改指标）**：

| # | 判据 | 阈值 |
|---|---|---|
| V1 | 20 封邮件的回复数 | ≥5 |
| V2 | 3 次对话中承认"这是售前缺口"的 | ≥2 |
| V3 | LOI 或付费 | ≥1（金额不限） |

**全不达标 → 判定 P-A 不成立，Prune 回到"只做分发、不谈商业化"两季**（与既有结论一致）。这条写死，避免每季度重复讨论同一个问题。

## 11. 与当前产品的关系：三层让渡模型

### 11.1 关系定性

**P-A 不是第二条产品线，是同一个读数层的第二个出口。** 当前产品面向「人」（看、判断、决定删不删）；P-A 面向「另一个厂商的售前」（出具、背书、集成）。内核是同一份代码，消费者不同。

所以平衡问题不是「两条路线怎么分资源」，而是**「哪一层可以让，哪一层不能让」**。分不清层次，"平衡"就会变成每次谈判都重新吵一遍。

| 层 | 内容 | 可让渡性 | 谁的权限 |
|---|---|---|---|
| **内核层** | 探测逻辑（`footprint` / `lsof` / `nettop`）、口径（0 ≠ 读不到）、68 条白名单与 🟢🟡🔴 分级、四道护栏、只读底线 | **不可让渡** | 只有作者；客户提出即拒绝并解释 |
| **出口层** | 报告模板、字段映射、语言、品牌位、MCP/CLI 形态、聚合顺序 | **可让渡，但只走配置** | 作者 + 合同约定 |
| **商务层** | 联合品牌、定价、排他期、支持承诺、发票与采购材料 | **可让渡，但不进代码库** | 商务谈判 |

**一条判据**：客户需求落在哪一层，决定它能不能进 backlog。落在内核 → 拒绝；落在出口 → 用配置解，不开分支；落在商务 → 进合同，不占工程产能。

### 11.2 六个真实冲突与处置

| # | 冲突 | 客户的合理诉求 | 处置 | 越界信号 |
|---|---|---|---|---|
| C1 | 口径定制 | "把 swap 压力改成百分比展示，我们客户看得懂" | 出口层做**字段映射**（`swapUsedRatio`），内核口径不动 | 要求"改成和活动监视器一致"——那是换口径，拒绝 |
| C2 | 品牌与文案 | 换成他们的语言、加 logo、改标题 | 允许，但绑定两条：**口径说明不可删；禁止只截取大数字** | 要求删掉"不确定/读不到"的表述 |
| C3 | 功能插队 | "先给我们加个 XX 报警" | 进 backlog 排队；要插队按天另计价（买的是工时，不是功能） | 以"合同已签"为由要求插队且不付费 |
| C4 | 双分支维护 | "给我们单独出一个构建" | **禁止分支**，只允许"配置包 + 编译期开关"，同一 commit 出两个产物 | 出现第一条长期维护的分支 → 立即停止 |
| C5 | 支持承诺 | "出问题多久响应" | 只写「版本节奏 + best effort」；专属支持单独计价、按月封顶 | 要求写入 24h SLA（单人做不到，写进去就是负债） |
| C6 | 叙事漂移 | 把 Prune 说成"开发机加速器""体检神器" | co-brand 物料必须过 README 同一条自检：**不新增无法自证的陈述** | 出现"提升性能""自动优化"类表述 |

### 11.3 资源配比（3 人日/周口径）

| 用途 | 常态 | 拿到 LOI 后 | 硬上限 |
|---|---|---|---|
| 社区主线（Wave 1 工程项） | 2.0 | 1.5 | 不低于 1.5 |
| 出口层（report / 契约 / 集成） | 0.75 | 1.0 | 不超过 1.0 |
| 商务对接（邮件、对话、合同） | 0.25 | 0.5 | **不超过 0.5，连续 4 周超限即止损** |

**优先级裁决序（冲突时按序裁，不复议）**：
`口径正确性 > 契约稳定 > 社区主线体验 > OEM 定制 > 新探测能力`

这条顺序的作用不是排序，是**让"拒绝客户"变成一件不需要勇气的事**——它只是执行第 4 条。

### 11.4 一条反直觉的平衡点

**OEM 客户越多，越要保证社区版先发。** 因为"免费版永远先拿到、且不阉割"是这个 MIT 项目唯一的信任基础，也恰恰是 OEM 愿意付钱的理由——他们买的不是代码（代码他们能 fork），是"这东西在社区里活着、有人在维护"。一旦社区版落后于 OEM 版，你卖的东西就消失了。

**具体规则**：任何版本，社区版与 co-brand 版同一 commit 构建；co-brand 版只能"多一层皮"，不能"多一个功能"。

## 12. 什么时候该砍 P-A（止损线）

| # | 触发条件（任一命中即停） | 动作 |
|---|---|---|
| S1 | 90 天验证 V1/V2/V3 全不达 | 停止商务投入，回到只做分发两季（与既有结论一致） |
| S2 | 客户要求修改内核口径 **≥1 次**且坚持 | 终止该客户谈判，不做例外 |
| S3 | 商务对接占用 **>1 人日/周连续 4 周** | 暂停新客户，先修交付物与定价 |
| S4 | 出现第一条需要长期维护的客户分支 | 立即回滚为配置包，否则放弃该客户 |

S2/S4 是"不平衡已经不叫平衡"的判据：一旦让渡突破内核层，P-A 就从"第二个出口"变成"第二个产品"，单人无法承担。
