# Prune · 泄漏嫌疑判定（M3 / B5）实现方案

> 2026-10-26 · 上游：`prune-feature-spec-v2.md` §6 / `m2-memory-plan.md` §1 §5.4
> 本文只解决 **B5 泄漏嫌疑判定**。M3 的 CLI / MCP / `NSPopover` / A6 不在本期。

---

## 0. 结论先行

| # | 结论 |
|---|---|
| 1 | 判定单元必须是**单进程序列**，不能是家族总量。真实库里 Cursor 家族 6 h 从 6.4 GB 涨到 19.0 GB，但同期进程数 11 → 62——涨的是深探覆盖，不是内存。按家族判定会立刻误报 12.6 GB |
| 2 | 只有「净增长」不够。真实库里唯一超阈值的进程（pid 50392，30 min +633 MB/+80%）其实是**一次性阶跃**：36.7 MB 平台期 → 单点跳到 686 MB → 平台 3 h → 再单点跳到 1425 MB。必须加**阶梯排除**，否则第一次上线就误报 |
| 3 | 判定跑在 Rust（`prune-core::leak`），前端只消费结论 + 证据。回归、阈值、良性名单全部可单测，不依赖 UI 才能验证 |
| 4 | 数据来自 M2 已落地的 SQLite 序列（5 min 粒度 / 保留 7 天），**本期不改表结构**，只加一个查询 |
| 5 | 判定结果进 `MemSnapshot.leaks`，随现有 `mem://snapshot` / `mem://deep` 一起到前端，不新增事件通道 |

## 1. 本期范围

| 做 | 不做 |
|---|---|
| 单进程序列回归（斜率 + R²）+ 四条数值门槛 | 任何「杀掉进程 / 释放内存」动作 |
| 阶梯排除、数据空洞拒绝、良性名单（代码层） | 「泄漏原因分析」这类伪科学归因 |
| 证据可视化（增长量 + 时长 + R² + 曲线） | 机器学习 / 历史自学习阈值 |
| 家族聚合展示（把命中的进程按家族归并成一行） | 通知推送、后台告警 |
| 「数据不足」显式状态（首次运行 < 30 min 时） | CLI / MCP（M3 后续） |

## 2. 真实库基线（2026-10-23 本机 `prune.db`，5.96 h / 68 个时间点 / 4441 行）

这是 M2 开发期真实跑出来的序列，是本文所有规则的实际考验对象。

| 观察 | 数据 | 对判定的影响 |
|---|---|---|
| 家族级聚合不可用 | Cursor 家族：6 425 MB（11 进程）→ 19 032 MB（62 进程） | 增长 12.6 GB 全是覆盖变化 → **改用单进程序列** |
| 单进程序列稳定 | 68 个时间点里，pid 171/674/6417… 全程有值，5 min 一点 | 序列足以做回归，无需补点 |
| 真实阶跃（必须排除） | pid 50392：36.7 MB（13:27–13:48 共 9 点平台）→ **13:53 单点 686 MB** → 平台 3 h → **17:39 单点 1425 MB** | 30 min 窗口 +633 MB / +80%，四条数值条件全过 → 只看数字必然误报 |
| 真实缓慢增长（应放过） | pid 674：886.6 → 1218.8 MB（6 h，+332 MB），30 min 窗口 +94 MB / +8.4% | 绝对门槛挡住；这类「Electron 主进程慢涨」正是不能报的噪音 |
| 采样有抖动 | 同一 5 min 轮内偶有 5~21 s 的重复点（手动刷新增补） | 回归必须用**真实 ts** 做 x，不能按点序号 |

> 也就是说：**本机真实数据在正确规则下应得出 0 个疑似泄漏**。任何一条规则改松都会在 pid 50392 上立刻误报——这是验收的负例基准。

## 3. 判定算法

### 3.1 输入：单进程序列

```
ProcSeries { pid, start_time, family, name, samples: [(ts, footprint)] }
```

- 序列按 `pid + start_time` 切分：`start_time` 不同的同 pid 行属于不同进程，绝不接续（pid 复用）。
- 只取 `footprint IS NOT NULL` 的行（RSS-only 行不参与判定，避免口径混用）。
- 查询窗口 = 判定窗口 + 30 min 余量（用于找窗口起点那一侧最近的点）。

### 3.2 判定条件（全部满足才标记）

| # | 条件 | 阈值 | 理由 |
|---|---|---|---|
| 1 | 存在时长 ≥ 窗口 | 30 min（GC 语言 60 min） | 刚启动的应用在正常预热，不能判 |
| 2 | 观测覆盖 ≥ 窗口的 80% | 首点 ts ≤ now − 0.8×窗口 | 只看 5 min 数据就说「涨了」是耍流氓 |
| 3 | 窗口内点数 ≥ 6 且无 > 15 min 空洞 | — | 5 min 粒度下 30 min 应有 6~7 点；有断档说明 Prune 没在跑 |
| 4 | 净增长 > 150 MB | GC 语言 300 MB | 绝对值下限，挡噪音 |
| 5 | 净增长 / 窗口起点值 > 40% | — | 3 GB 的进程涨 200 MB 不算异常 |
| 6 | 斜率 > 0 且 R² > 0.70 | — | 必须是「持续爬升」，不是锯齿 |
| 7 | **最大单点跃升 ≤ 总增长的 60%** | 0.6 | **实测新增**：一次性加载/新开窗口是阶跃，不是泄漏 |
| 8 | 不在良性名单 | 见 §3.5 | Chrome / VM / 系统进程的增长由页面与虚拟机驱动，报了也不可行动 |

### 3.3 回归口径

- `x` = `(ts − window_start) / 60`（分钟，用真实时间戳），`y` = footprint（字节）。
- 普通最小二乘：`slope`、`intercept`、`r2 = 1 − SS_res / SS_tot`。
- `SS_tot = 0`（完全平线）时 `r2 = 0`，不算通过。
- `slope` 对外换算成 **MB/小时** 展示（比 bytes/s 可读）。

### 3.4 阶梯排除（条件 7 的细节）

```
steps = 相邻点差分（正负都算）
max_step = max(|step|)
max_step > 0.6 × 净增长  →  判为阶梯，不标记
```

- 纯阶跃（pid 50392）：净增长 633 MB，max_step 633 MB → 100% > 60% → 拒绝 ✅
- 教科书式泄漏（每 5 min 稳定 +30 MB）：净增长 180 MB，max_step 30 MB → 17% → 通过 ✅
- 混合形态（一半爬升 + 一次大跳）：max_step 占比 70% → 拒绝（宁可漏报）

### 3.5 良性名单（代码层表，不是提示）

| 类别 | 匹配方式 | 理由 |
|---|---|---|
| 浏览器 | family ∈ {Chrome, Safari, Firefox, Arc}，或 exe 含 `com.apple.WebKit` | 页面与缓存驱动，涨落是正常行为 |
| 通用 Electron | family == `Electron` | 同上（具名 Electron 应用不在此列，见决策点 D-L2） |
| 虚拟机 / 容器 | family ∈ {Docker}，或 exe/name 含 qemu / VirtualBox / VMware / Parallels / colima | 内存由 guest 决定 |
| 系统进程 | exe 前缀 `/System/` `/usr/libexec/` `/usr/sbin/` `/System/Library/` | 不归用户处置 |
| 自身 | family == `Prune` | 不评判自己 |

### 3.6 GC 语言识别

`name` / `family` 命中 `node` / `java` / `jvm` / `openjdk` / `golang` / `go-build` → 窗口 60 min、绝对门槛 300 MB。

**不认裸词 `go`**：会命中 `Django`、`Google Chrome Helper` 之类无关名字。Go 编译后的二进制认不出来时按普通进程判——门槛更低，只会多报不会漏报。

理由：GC 语言的堆是阶梯式增长后回收，30 min 窗口内很容易出现「涨了 200 MB 还没 GC」的假象。

## 4. 数据模型

```rust
pub struct LeakItem {           // 一个命中进程
    pub pid: i32,
    pub start_time: u64,
    pub family: String,
    pub name: String,
    pub footprint: u64,         // 窗口末值
    pub growth: u64,            // 窗口净增长
    pub growth_ratio: f64,      // growth / 窗口起点
    pub window_secs: i64,       // 30 min 或 60 min
    pub points: usize,
    pub slope_mb_per_hour: f64, // MB/h（单位写进字段名，前端不再猜）
    pub r2: f64,
    pub step_ratio: f64,        // 最大单点跃升 / 净增长（证据透明度）
    pub gc_runtime: bool,
}

pub struct LeakReport {
    pub items: Vec<LeakItem>,   // 按 growth 降序
    pub observed: usize,        // 参与判定的进程数
    pub insufficient: usize,    // 序列不够长（首次运行）
    pub benign: usize,          // 良性名单排除
    pub below: usize,           // 条件未达标
    pub window_secs: i64,
    pub updated_at: Option<i64>,
    pub note: Option<String>,   // 「序列库不可用」等
}
```

`below` / `benign` / `insufficient` 三个计数是为了让 UI 能说「检查了 42 个进程，3 个数据不足」——沉默地「没问题」和「没在检查」在用户眼里没有区别。

## 5. 计算时机与成本

- **触发点**：每轮 5 min 深探落库之后（此时序列刚被写入，判定看到的是最新数据）。
- **成本**：一次查询取 90 min 窗口（≈ 18 轮 × 64 进程 ≈ 1 200 行），回归在内存里做，微秒级。相对 footprint 深探（百 ms 级）可忽略。
- **启动即有结果**：`sampler::run()` 首轮就调用深探轮 → 立刻用历史库算一次，用户不必等 5 min。
- **无库时**：`LeakReport` 返回 `note = "序列库不可用，无法做泄漏判定"`，UI 显示说明而不是「0 个泄漏」。

## 7. UI

### 7.1 面板（380×560）

「应用」tab 顶部：仅当 `items.length > 0` 时出现一行提示条

> ⚠ 疑似内存泄漏 · 2 个进程 · 30 min 合计 +380 MB  → 点击进主窗口

无命中时**不显示任何占位**（沉默即正常）。数据不足时在概况 tab 脚注一句「泄漏判定需连续观测 30 min（当前 12/30）」。

### 7.2 主窗口

- 「应用内存」tab：命中家族的行首加 `<Badge tone="warn">疑似泄漏</Badge>`，行尾显示窗口增长量。
- 「系统概况」tab 顶部新增「疑似内存泄漏」卡片：每行 = 进程名 + 家族 + 当前占用 + 30 min 增长 + R² + 斜率，点击 → 选中该进程进检视器。
- 检视器：选中进程若命中，曲线卡片下加一段证据（窗口、增长、占比、斜率、R²、阶梯占比），并注明「这是统计判断，不是结论」。

| 允许 | 禁止 |

## 9. 决策点

| # | 决策 | 建议 | 备选 |
|---|---|---|---|
| **D-L1** | 判定单元 | **单进程**（家族只做展示归并） | 家族总量（实测会误报 12.6 GB，不推荐） |
| **D-L2** | 具名 Electron 应用（Cursor / VS Code / Slack）是否一律放过 | **不放过**——它们是用户可行动对象（能重启验证）；只排除 `Electron` 这个通用家族名与浏览器 | 全部 Electron 系放过（等于把 M3 主要价值放掉） |
| **D-L3** | 阶梯排除阈值 | **0.6**（最大单点跃升 > 净增长 60% 即拒绝） | 0.5 更保守 / 0.8 更宽松 |
| **D-L4** | 是否要求「连续观测 30 min」才判定 | **是**，并显式显示「数据不足 N/30 min」 | 用 start_time 直接判（会拿不足 30 min 的序列下结论） |
| **D-L5** | 是否新增 DB 表/字段 | **不改表**，复用 M2 的 `mem_process` | 加 `gc` 列（收益低，schema 变更成本高） |
| **D-L6** | 判定结果是否进快照 | **进**（复用现有事件通道，前端零新增拉取） | 独立命令 + 事件（多一条链路要维护） |

## 10. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 误报一次就失去信任 | 🔴 | 阶梯排除 + 良性名单 + 高 R² 门槛；文案只给「疑似」并展示全部依据 |
| 首次运行 30 min 内没有判定结果 | 🟠 | 显式显示「数据不足 N/30 min」，而不是假装没问题 |
| 序列库被清空/损坏后判定永久为空 | 🟡 | `note` 字段区分「库不可用」与「无命中」 |
| 长时间运行后 7 天保留期截断窗口 | 🟢 | 判定窗口 60 min ≪ 7 天，不受影响 |
| GC 语言被频繁误判 | 🟠 | 门槛翻倍 + 60 min 窗口，实测调 |

## 11. 验收标准

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 合成序列：稳定爬升 → 命中；阶跃 → 拒绝；锯齿 → 拒绝；平线 → 拒绝 | 单测（各一组） |
| 2 | pid 复用（同 pid 不同 start_time）不接续成一条序列 | 单测 |
| 3 | 良性名单：Chrome / Docker / 系统进程 / Prune 自身零命中 | 单测 |
| 4 | GC 语言门槛翻倍生效（Node 进程 200 MB 不命中，350 MB 命中） | 单测 |
| 5 | 数据不足：序列 < 6 点或无覆盖 → `insufficient` 计数 +1，不产生 item | 单测 |
| 6 | **真实库实测**：读 2026-10-23 的 `prune.db`（6 h / 68 点），结论应为 **0 个疑似泄漏**；pid 50392 必须被阶梯规则拒绝，且原因可见 | `cargo run --example leak-probe` |
| 7 | 前端：无命中时面板不出现提示条；命中时显示增长量与「疑似」措辞 | 构建 + 代码复核 |
| 8 | 全量门禁：`cargo test --workspace` / `cargo check -p prune-app` / `pnpm build` 全绿 | 命令 |

## 13. 实施偏差记录（2026-10-26，按实测回扫）

| # | 方案原定 | 实际落地 | 原因 |
|---|---|---|---|
| 1 | §3.6 GC 识别含裸词 `go` | 只认 `golang` / `go-build` | 裸 `go` 会命中 `Django`、`Google Chrome Helper` |
| 2 | §4 `slope_per_hour` | `slope_mb_per_hour` | 单位进字段名，前端不必再猜一次 |
| 3 | 良性判定在数值判定之后 | **移到最前** | 否则 Chrome 这类会被计入「数据不足」，面板脚注会误报「数据不够」 |
| 4 | §3.2 未定义 `start_time` 未知时的行为 | 退回用序列跨度判存续时长 | 历史库里可能有 `start_time = 0` 的脏行，不能因为缺这个字段就永远不判 |
| 5 | §3.2 条件 2「覆盖 ≥ 窗口 80%」 | 同样加严到「首点距窗口起点 ≤ 20% 窗口」 | 实测发现：只取最后几个点（窗口内实际只覆盖 15 min）也能凑够 6 点，会被当成 30 min 判定——注入验证时踩到过 |

验收结果见 `docs/m3-leak-acceptance.md`。
