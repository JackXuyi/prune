## 0. 结论先行

1. **不做通用内存监控工具**——iStat Menus / Stats / eul / Activity Monitor 已占满，没有生存空间。
2. **不做「内存清理」**——释放内存提速是伪科学，且这条路上全是智商税软件。
3. **只做三件事**：把 macOS 藏起来的**内存压力**摆到菜单栏、用时间序列判定**哪个进程在漏**、对**开发环境专属垃圾**做安全回收。
4. **最大风险不在设计，在一个 API**：非特权进程能否拿到他人进程的 `phys_footprint`。这决定项目生死，必须在写任何 UI 之前验证（见 §3、§10）。

## 1. 产品定位

| 维度 | 定义 |
|---|---|
| 一句话 | 你的 Mac 卡，是因为谁在漏内存？ |
| 形态 | macOS 菜单栏原生 App（SwiftUI），另有独立窗口形态 |
| 受众 | 同时跑多容器 / 多服务 / 模拟器的开发者（与 Portlivo 受众重叠 90%） |
| 核心价值 | 把「内存占用百分比」这个**无用指标**，换成「压力 + 交换颠簸 + 泄漏嫌疑人」三个**可行动指标** |
| 不做 | 内存清理、风扇控制、温度监控、CPU 调度——不做 iStat Menus 全家桶 |

### 为什么「占用百分比」是无用指标

macOS 有压缩内存机制，**内存被占满是正常且期望的状态**。显示「已用 14GB / 16GB」只会引发焦虑且导向错误动作（去杀无辜进程）。真正决定卡不卡的是：

| 指标 | 含义 | 为什么有用 |
|---|---|---|
| **内存压力** | 可用内存（free + speculative + purgable + clean external + inactive）占总量比例 | 决定系统是否开始大量压缩/交换 |
| **交换颠簸** | `swapins` 增量的**速率**，而非 swap 总量 | swapin 速率飙升 = 机器真的在颠簸，这是卡顿的直接原因 |
| **泄漏嫌疑人** | per-process footprint 单调增长 | 定位到具体进程，才可行动 |

> Activity Monitor 把内存压力藏在窗口最底部一行，把 swap 藏在一个独立面板里。**这就是切入点。**

## 2. 目标场景（5 个真实场景）

| # | 场景 | 现状痛点 | Footprint 的动作 |
|---|---|---|---|
| S1 | 跑了半天 / 一天后 Mac 越来越卡 | 只能猜，或打开 Activity Monitor 对着一堆进程发呆 | 菜单栏直接显示压力档位 + 交换速率，点开看谁在涨 |
| S2 | 自己写的 node 服务内存泄漏 | 等到 OOM 崩了才发现 | 泄漏嫌疑人在膨胀到 300MB 时就打标记，并给出启动命令与项目路径 |
| S3 | Docker / OrbStack 吃掉 6GB | 知道是它，但不知道该不该杀 | 归入「容器」分组 + 给出内存上限调整指引 |
| S4 | Xcode DerivedData 累积到 40GB | 硬盘满才知道 | 每日后台扫描，进入「可回收」列表，一键清理 |
| S5 | 关掉的编辑器留下了孤儿 node 进程 | 完全看不见（无端口、无窗口） | 父子进程链断裂 + 无监听端口 = 僵尸判定，一键收走 |

## 3. 技术可行性（含 API 分级）

### 3.1 数据获取能力矩阵

| 数据 | 接口 | 权限 | 判定 |
|---|---|---|---|
| 系统级内存页统计 | `host_statistics64(HOST_VM_INFO64)` → `vm_statistics64` | 无需 | ✅ |
| 交换活动 | 同上，`swapins`/`swapouts` 累计计数 | 无需 | ✅ |
| 进程基本信息 / 路径 / 父子关系 | `proc_listallpids` + `proc_pidinfo(PROC_PIDTASKINFO/PROC_PIDTBSDINFO)` | 无需 | ✅ |
| 命令 / argv / env / CWD | `sysctl KERN_PROCARGS2` | 无需 | ✅ |
| 进程 CPU / 内存 RSS | `proc_pidinfo(PROC_PIDTASKINFO)` | 无需 | ✅ |
| **进程 `phys_footprint` / 压缩量** | mach `task_info(TASK_VM_INFO)`，需先 `task_for_pid` 取 task port | **可能需 root** | ⚠️ **待验证** |
| 堆内分配追踪（`heap`/`malloc_history`） | 目标进程 task port + 授权 | 需 root / 授权 | ❌ **不做** |
| 目录体积（Xcode / Simulator / 缓存） | `FileManager` 遍历 `~/Library/...` | 无需（不在 TCC 保护范围） | ✅ |
| 来源应用与前置 | PPID 链 + `NSRunningApplication.activate()` | 无需 | ✅ |

### 3.2 ⚠️ 核心门槛与三条备选路径

**问题**：`task_for_pid` 对非自身进程要求调用者具备 root 或 `com.apple.security.cs.debugger` 等授权。若验证失败，则拿不到 Apple 官方口径的 `phys_footprint`。

| 路径 | 做法 | 代价 | 评级 |
|---|---|---|---|
| **D1-A** | 退回 `pti_resident_size`（RSS）口径 | 多进程应用（Chrome / Electron）共享内存被重复计入，数值虚高；但对 node / docker / 自建服务基本准确 | 🟢 推荐首选 |
| **D1-B** | 上 `SMJobBless` 特权助手拿 task port | **摧毁「零权限」叙事**；增加审核与信任成本；与产品核心卖点冲突 | 🔴 不推荐 |
| **D1-C** | 只做系统级压力，放弃 per-process 精确内存 | 直接失去「泄漏判定」这个唯一差异化 | 🔴 不可接受 |

> **预判**：D1-A 大概率可行且够用。开发者场景的内存大户（node、Vite、Docker VM、Java）RSS 与 footprint 差异可忽略；**虚高的主要是 Chrome / Electron / VS Code** —— 而这几个恰好不需要做泄漏判定（它们的内存增长是标签页/插件导致的、且用户已知），可以直接从泄漏判定名单里排除。**这个巧合让 D1-A 的缺点几乎被抵消。**

### 3.3 内存压力的公开近似算法

Activity Monitor 的压力值来自私有 API。公开数据下的近似：

```
可用页 = free_count + speculative_count + purgeable_count + external_page_count(clean) + inactive_count
压力   = 1 - 可用页 / 总页数

档位：  < 60%  →  绿（Nominal）
       60–80%  →  黄（Warn）
       >  80%  →  红（Critical）
```

🔴 **必须做的一件事**：拿一台真机，开着 Activity Monitor 与 Footprint 对照，把这套近似公式的档位阈值**校准到与系统一致或接近**。公开近似若不校准，用户会觉得「这软件读数不对」，信任瞬间崩塌。列入 M0 必办项。

```
       │ 概览      │  图标/名称    │  footprint 曲线 │
       │ 全部进程  │  footprint     │  内存构成       │
       │ 泄漏嫌疑  │  趋势 sparkline│  命令 / 路径    │
       │ 可回收    │  状态标记      │  来源应用       │
       │ 容器      │               │  操作按钮       │
       │ 活动记录  │               │                │
       └──────────┴───────────────┴────────────────┘
                  ⌘K 命令面板 · CLI
```

### 4.2 功能清单与优先级

#### M1 — 看得见（最小可用）

| 功能 | 说明 | 依赖 |
|---|---|---|
| 菜单栏压力环 | 颜色档位 + 交换速率 + 前 3 名 | 3.3 近似算法 |
| 进程列表 | 按**开发者视角**分组：自建服务 / 编辑器 / 浏览器 / 容器 / 模拟器 / AI Agent | 进程画像复用 Portlivo 路线 |
| 每行画像 | 图标 + 项目名 + footprint + 命令 + 来源应用 + CPU | `KERN_PROCARGS2` + PPID 链 |
| 隐藏噪音 | 系统守护进程、WindowServer 等默认隐藏 | 黑名单 |
| 自适应采样 | 窗口打开 10s，仅菜单栏 60s | — |

> **明确不做 2s 轮询**。Portlivo 用 2s 是因为端口需要即时响应；内存变化是分钟级的，2s 纯属浪费电。这是有意的差异化。

#### M2 — 判得出（差异化核心）

| 功能 | 说明 |
|---|---|
| 24h 趋势 | 每进程环形缓冲，1min 精度保留 24h（1440 点 × 8B × 100 进程 ≈ 1.2MB） |
| **泄漏嫌疑判定** | 见 §5 算法 spec |
| 交换颠簸告警 | `swapins` 速率超阈值 → 通知，并直接指出当前最大可用内存消耗者 |
| Inspector 曲线 | 单进程完整时间线 + 关键事件标记 |
| 活动记录 | 按天分组的启动/退出/OOM 记录 |

#### M3 — 收得掉（闭环）

| 功能 | 动作 | 风险等级 |
|---|---|---|
| 僵尸进程回收 | 父进程链断裂 + 无监听端口 → 一键 kill | 🟢 |
| iOS Simulator 关闭 | 无连接设备时建议关闭 | 🟡 丢状态 |
| Xcode DerivedData | 每日扫描，一键清理（保留最近使用） | 🟡 下次编译变慢 |
| 包管理器缓存 | npm/pnpm/yarn/CocoaPods/Gradle 缓存体积，给出清理命令 | 🟢 |
| 容器内存指引 | 不自动改配置，给调整入口 | 🟢 只指引 |

> **红线：M3 不碰 Chrome 标签页**（需辅助功能权限）、**不碰 `sudo purge`**（需 root）、**不做任何「释放内存」按钮**。

## 5. 泄漏嫌疑判定算法（M2 技术核心）

### 5.1 输入

每 10s（窗口打开）/ 60s（后台）采样一次每进程的 `phys_footprint`（D1-A 退回时为 RSS），写入环形缓冲。

### 5.2 判定条件（全部满足才标记）

```
1. 存在时长 > 30min                        // 排除启动预热期（Vite / node 冷启动会涨）
2. 近 30min 净增长 > 150MB 且 > 40%         // 绝对 + 相对双门槛，防小进程误报
3. 线性回归斜率 > 0 且 R² > 0.70            // 排除缓存型锯齿波动
4. 不在良性名单内                            // 见下
5. 若为 GC 语言（Java/Go/Ruby），门槛提高至 300MB / 60min   // GC 天然锯齿上涨
```

### 5.3 良性名单（直接排除）

Chrome / Edge / Safari / Arc、Electron 类应用（VS Code / Cursor / Slack / Discord）、虚拟机与容器主进程、系统进程。

> 理由：它们的内存增长来源于标签页与插件，用户自己清楚，且杀掉代价高。**误报一次的信任成本，远高于漏报一次。**

### 5.4 输出与措辞

| 级别 | 条件 | UI 措辞 |
|---|---|---|
| 🔴 疑似泄漏 | 全部条件满足 | 「疑似内存泄漏 · 30 分钟 +412MB」 |
| 🟡 持续膨胀 | 满足 2、3，时长不足 | 「持续膨胀中」 |
| ⚪ 正常 | — | — |

**措辞硬约束：永远说「疑似」，永远不说「你的 XX 泄漏了」。** 这是概率判定，必须给出可解释的依据（增长量 + 时长 + 曲线），并提供「忽略此进程」入口。

## 8. 竞争与差异化 ⚠️ 已推翻

> **本节结论作废。** 2026-10 竞品实测后确认：本节假设的「唯一护城河」三条（开发者视角分组 / 泄漏嫌疑判定 / 开发环境安全回收）已全部被现成产品覆盖，其中 Mac Performance Monitor 为免费开源 MIT，且其泄漏判定的措辞克制与本方案完全一致。
>
> 完整对比、剩余真空与三条战略选项见 **`footprint-competitive-analysis.md`**。

| 竞品 | 实际价格 | 实测结论（取代原判断） |
|---|---|---|
| Activity Monitor | 免费 | 基线，不是对手 |
| **Mac Performance Monitor 2.2** | **免费 · MIT** | 🔴 **最接近的对手**：菜单栏+记录器、泄漏指示、压力事件、分组、SQLite 历史、`mpm` CLI + MCP server |
| **Vitals** | **$9 首发 → $29** | 🔴 **商业上最强**：App 分组 + 30 天历史 + 内存增长告警 + **dev servers 按项目可停**（= Portlivo 核心） |
| **ProcXray** | **$15 一次性** | 🟠 进程画像比本方案更深（env / cwd / dylib / 签名校验） |
| iStat Menus 7.20 | $11.99 单 / $14.99 家庭 | 传感器最全，压力/交换已覆盖 |
| Stats / eul / MenuMeters | 免费开源 | 红海已被免费吃透 |
| Memory Cleaner 类 | 免费~订阅 | 仍为营销对立面，非功能对手 |

**唯一剩余真空**：开发环境的**磁盘侧**可回收资源（DerivedData / node_modules / Docker 层 / Simulator / 包管理器缓存）——监控工具不愿碰、清理工具看不懂的交叉地带。

**待决策**：A 不做 / **B 转向资源回收（推荐）** / C 极窄开源换心智。

## 9. 风险清单

| 严重度 | 风险 | 应对 |
|---|---|---|
| 🔴 | `phys_footprint` 需特权，D1-A 也失效 | M0 阶段验证；最后退路是只做系统级 + 可回收（砍掉泄漏判定） |
| 🔴 | 压力近似公式与系统读数偏差大，被指「不准」 | M0 阶段必须与 Activity Monitor 对照校准 |
| 🟠 | 泄漏判定误报，用户觉得是玄学 | 措辞「疑似」+ 展示依据 + 良性名单 + 忽略入口 |
| 🟠 | 长时运行的自身内存与耗电 | 环形缓冲固定上限 + 后台降频 + 不在后台做任何目录扫描 |
| 🟡 | 与 Portlivo 受众重叠但功能重叠度低，可能被当作「另一个监控器」 | 营销上直接对标「Activity Monitor 不会告诉你的三件事」 |
