# M10 应用资源预览 Tab 方案（含 UI wireframe）

> 状态：**已实施（2026-11-05，A0–A3）**，真机走查待做
> 前置：M2（内存/CPU）、M5（整机 CPU）、M7（端口）、M8（应用资源卡 + 磁盘三层）、M9（统计 tab）
> 需求：新增一个**应用级**资源预览 tab —— 一屏横向对比每个应用的进程数 / CPU / 内存 / 存储 / 端口 / 网速；页面要求**有趣直观**
> 修订：v2 加进程数 + 比例条 + 摘要条；v3 展示形态由表格改为卡片网格；**v4 默认排序内存降序 + 默认只展示 Top 12，其余折叠可展开**（本版）

## 0. 结论先行

| 决策 | 结论 | 一句话理由 |
|---|---|---|
| 做**新 tab「应用资源」**，位置在「统计」之后 | **双列卡片网格** + 卡片跨列展开 | 用户要的是「每个应用一张画像」+ 跨应用对比；卡片能同时装下徽标、条、走势，表格只能装数字 |
| **卡片而不是表格**（v2 表格方案作废） | 同高卡、固定指标行序、同刻度条 | 卡片更好看更好读，代价是**失去列对齐**；用「版式一致 + 条同刻度 + 排序控件」三条补偿，取舍写在 §4.0 |
| 与 M8 的关系：**M8 的 `AppResourceCard` 保持不动** | 本 tab 另有紧凑卡 `ResourceCard`（`AppResourceGrid.tsx` 内）+ 卡内详情区 | 实施时确认：M8 卡是「六格 + 测量按钮」的单应用深看，硬塞进网格会同时丢掉密度和对比；复用的是**口径与测量命令**，不是同一个组件（避免为了复用而把 M8 卡改成四不像） |
| **进程数进卡片头部徽标** | `54 进程`，≥20 警示色；同时是排序字段之一 | 用户点名要；卡片没有列，徽标位最省地方且一眼可见 |
| 排序从「点表头」改为**排序段控件** | `内存 ▾ / CPU / 进程 / 磁盘 / 端口 / 下载` + 方向切换 | 卡片没有表头，排序必须显式给控件；这反而是卡片布局下找异常的主路径 |
| **比例条跨卡同刻度**（分母 = 全表最大值） | 内存 / 磁盘 / CPU / 下载 / 上传五条 | 卡片失去列对齐后，同刻度的条是**唯一还能横向比较**的锚点，否则直接变装饰 |
| 展开 = 卡片**跨两列长大**，同时只展开一张 | `grid-column: 1 / -1` | 卡内展开不打断网格节奏；跨列后详情有整行宽度装端口清单与三层磁盘 |
| **默认只显示 Top 12**，其余折叠 | 默认排序内存降序 → 前 12 张卡 = 内存前 12 名；底部「展开剩余 36 个」 | 48 张卡滚 8 屏没人会看完；默认 12 张 ≈ 2 屏，正好是「谁在吃内存」的答案集 |
| 折叠**不是过滤**：比例条分母仍按全量算 | 分母 = 全部 48 个（过滤前）最大值 | 若按 12 个算，展开剩余时全屏条长会突然缩水，视觉上像数据变了 |
| 搜索态**不受 Top 12 限制** | 有关键字时显示全部匹配项，折叠门控隐藏 | 「搜了却搜不到」是最糟的体验，折叠只服务默认浏览 |
| 网速**能做**：macOS `nettop` 流式差分 | 1 s 一采样，`external`（非回环），仅内存不落盘 | 实测无 root 可用、22 ms/轮、~14–19 个有流量进程；M8 说的「无公开 API」指字节计数 API，CLI 是可替代路径 |
| 网速不可用 → 卡内该行「不可读」+ 顶部说明条 | 不显示 0、不估算 | nettop 是私有 CLI 无格式契约，解析失败必须降级 |
| 磁盘卡内只显示**本体 bundle**（批量一次测完） | 缓存/数据在展开区按需测（M8 现成） | 实测 20 个 .app `du` 共 1.96 s；缓存/数据 0.25–4 s/应用，进不了首屏 |
| Windows 首期网速行显示「—」+ 平台说明 | 不接 ETW | per-process 字节统计在 Windows 要 ETW 实时会话，超出本里程碑 |

## 1. 需求理解与边界

**用户问题**（UI 每个决策对照检查）：

1. 「Cursor 到底占了我多少资源？」——一张卡上进程 / CPU / 内存 / 磁盘 / 端口 / 网速全在
2. 「谁在偷跑网速？」——排序切到「下载」，第一张卡就是答案
3. 「哪些应用占了我 10 GB 以上的盘？」——排序切到「磁盘」
4. 「谁开了几十个进程在后台蹲着？」——排序切到「进程」，或看头部的进程徽标
5. 「不用点任何东西，一眼看出大户」——默认内存降序 + 只给 Top 12，打开即答案；同刻度比例条 + 阈值变色辅助扫视
6. 「点进去看细节」——卡片跨列长大，端口清单 / 进程 Top / 磁盘三层全在卡内
7. 「剩下 36 个我偶尔想看」——底部「展开剩余 36 个」，不藏死在滚动里

**边界**：

- ✅ 做：双列卡片网格（6 域 + 搜索 + 排序控件 + 跨列展开 + Top 12 折叠）+ 网速采集通道 + 卡内比例条 + 大户 spotlight
- ❌ 不做：系统级总览（M9 已有）、进程树（内存·应用 tab 已有）、卸载/清理入口、历史趋势（只有实时值 + 卡内 60 s 网速走势）、仪表盘式图表、分页（折叠 ≠ 分页，不做页码）

### 1.1 为什么要新 tab（承认 M8 的判断被推翻）

M8 方案 §0 写过「不加 tab，避免重复应用 tab」。那是**五域聚合**阶段，用户动作是「看这一个应用」。本次多出两样 M8 没有的东西：

1. **网速**——M8 判定「macOS 无公开 API，不做」，现在有 CLI 路径；
2. **横向对比**——排序找异常，而不是深看单个。

所以新 tab 成立；M8 的卡片不重复实现，直接升级复用。

### 1.2 为什么改用卡片（承认 v2 表格判断被调整）

v2 选表格的理由是「对齐扫视效率最高」。卡片在这个 tab 上赢在另外三点：

1. **一张卡 = 一个应用的画像**。六个域挤在表格一行里只能放数字，卡片能放徽标、条、走势，读起来是「Cursor 很能吃 CPU」而不是「Cursor: 188%」；
2. **展开有地方**。表格展开是插入一行，宽度受限于行；卡片跨两列展开后有整行宽度装端口清单和磁盘三层；
3. **用户明确要卡片**。这是最直接的理由。

代价必须写明：**每屏可见应用数从 ~10 行降到 ~6 张卡**，跨行对齐扫视弱化。补偿手段见 §4.0；进一步用**默认 Top 12 折叠**把首屏从 8 屏压到 2 屏（§4.2），让「打开就看前 12 名」成为默认动作。若真机走查发现扫视效率明显下降，A2 预留 `variant="compact"`（单列紧凑行）开关，但**不进首期默认**。

## 2. 现状诊断（代码级 + 实测）

| 域 | 现状 | 缺口 |
|---|---|---|
| 进程数 | `FamilyMem.processCount` ✅（M2 起就有） | 无（此前只在 M8 卡片里出现，未参与排序/概览） |
| CPU | `FamilyMem.cpu` + `cpuCovered`（单核口径，下界语义）✅ | 无 |
| 内存 | `FamilyMem.footprint / rss / swapped` ✅ | 无 |
| 端口 | `PortSnapshot.entries`（关注层 `watched`）✅ | 无（tab 可见时一次性扫描，同 M9） |
| 连接 | `connsByPid`（ESTABLISHED / CLOSE_WAIT）✅ | 无 |
| 磁盘 | M8 `app_disk` 三层按需 + 30 min TTL ✅ | 缺**批量只测 bundle 本体**的便宜路径（每张卡都要一个数） |
| 网速 | **无** | 全新：`nettop` 流式采样 + 差分 + 按 pid 归并到家族 |
| 卡片组件 | M8 `AppResourceCard`（单应用、六格、含测量按钮）✅ | 需拆成 `grid`（紧凑，网格用）/ `detail`（展开用）两个 variant |

**实测（2026-11-04，M2/16G，本机）**：

| 项 | 结果 |
|---|---|
| `nettop -P -x -l 1 -J bytes_in,bytes_out -t wifi` | **22 ms**，输出 `进程名.pid  bytes_in  bytes_out`（累计；名字截断到 15 字符） |
| `nettop -P -x -L 0 -s 1 -t external`（流式 CSV） | 3.2 s 收到 4 个样本共 63 行，**~14–19 个有流量进程/样本**；列含 `time` 可做样本边界 |
| 是否需要提权 | **不需要**，普通用户直接可跑；输出含其他进程（同用户） |
| `du -sk` 20 个 `/Applications/*.app` | **1.96 s**（热缓存），34 个 .app 总计 |
| M8 结论复用 | 缓存/数据层 0.25–4 s/应用 → 不能进卡片首屏 |

**解析要点（已踩）**：

- 进程名会被**截断**（`Google Chrome H.1281`），且可能含非 ASCII（`小鸡快跑-…`）→ **只按末尾 pid 匹配**，绝不按名匹配；
- 同一 `(名称, pid)` 可能多行（不同 socket / 接口）→ 先按 `(样本, pid)` 求和，再做差分；
- 样本边界用 `time` 列的 `HH:MM:SS` 前缀分组（样本内各行时间戳差几微秒，不完全相同）。

## 3. 口径定义（正确性核心）

### 3.1 网速（新）

| 字段 | 口径 | 措辞 |
|---|---|---|
| `downBps` / `upBps` | 相邻两次 nettop 样本的**累计字节差分 ÷ 间隔**，按 pid 求和后归并到家族 | 卡内「↓ 120 KB/s」 |
| 接口范围 | `-t external`（排除 loopback）：这是「网速」，不是本机回环流量 | tooltip：「仅非回环接口；localhost 转发（vite HMR 等）不计入」 |
| 家族归并 | 家族成员 pid 集合 → 成员速度求和 | 与 CPU/内存的家族口径一致 |
| 首轮 | 只有 1 个样本 → 无差分 → **null，显示「采样中…」**（不是 0） | |
| 进程不在样本里 | 视为 **0 B/s**（nettop 已启动但该进程无流量） | 与「未采样」严格区分 |
| 采集失败 | nettop 缺失/退出码非 0/连续 3 个样本解析不出 → 状态 `unavailable` + 原因 | 所有卡片的网速行「不可读」+ 顶部说明条 |
| 不落盘 | 只在内存态，进程退出即丢（同 port 快照的隐私口径） | |

**明确不做的**：流量累计总量（只有速率）、历史曲线、按域名/对端分解、Windows 首期。

### 3.2 磁盘（卡内行 vs 展开区）

| 位置 | 口径 | 成本 |
|---|---|---|
| 卡内「磁盘」行 | **仅本体 bundle**（`*.app` 的 du），批量一次算完，TTL 30 min | 20 个 app ~0.5 s（8 路并行） |
| 展开区 | M8 三层（本体/缓存/数据，按需按钮触发） | 0.25–4 s/应用 |
| 无 bundle 的家族 | 「—」（CLI 工具、系统守护进程没有 .app） | 一致于 M8「宁可空白不猜」 |

### 3.3 卡片内各域（沿用既有口径，不新造）

| 域 | 来源 | 空值语义 |
|---|---|---|
| 进程数 | `FamilyMem.processCount` | 恒有值；≥20 用警示色（进程爆炸信号，Chrome/Electron 常见） |
| CPU | `FamilyMem.cpu`（单核，可 >100%） | null = 「—」；`cpuCovered < processCount` 标「下界」 |
| 内存 | `totalOf(family)`（footprint 优先，未深探按 RSS） | 有未深探成员时前缀「≈」 |
| 端口 | 关注层 `watched` 且 listener 属于该家族；对外暴露加橙点 | 端口未扫描 → 「—」+ 顶部提示，**不显示 0** |
| 连接 | `connsByPid` 家族求和，ESTABLISHED | 未扫描 → 「—」 |

### 3.4 比例条口径（卡片布局下最关键）

- 内存 / 磁盘 / CPU / 下载 / 上传五条，条高 3 px，长度 = `值 ÷ 分母 × 卡内容宽度`。
- 分母用**全表最大值**而不是系统总量：跟总量比，除第一张卡外全是看不见的细线，卡片的对比意义就没了。
- **卡片布局下条是唯一横向锚点**：卡片没有列对齐，若每条还各算各的刻度，就成了纯装饰。所以：同刻度、条起点同 x、条长同基准宽度。
- 最大值为 0 / 不可读时该行不画条（不画 ≠ 画 0 宽度）。
- 分母的**唯一合法变化来源**（按优先级）：

| 场景 | 分母 | 原因 |
|---|---|---|
| 默认 / 切排序 | 全部 48 个应用的最大值 | 切排序时分母不变，条长稳定 |
| Top 12 折叠 / 展开剩余 | **仍是全部 48 个** | 折叠只是「暂时不渲染」，不是过滤。若按 12 个算，点开剩余瞬间全屏条长缩水，看起来像数据变了 |
| 搜索过滤 | 当前匹配集合的最大值 | 显式过滤意图；否则在小集合里条全是贴底细线，失去比较能力 |

- 一句话原则：**分母只看「用户过滤了什么」，不看「屏幕渲染了几张」**。

## 4. UI wireframe

### 4.0 卡片布局的直观性补偿（取舍声明）

卡片失去列对齐，靠四条补回来：

| 补偿 | 做法 |
|---|---|
| 版式一致 | 所有卡同高、指标行序固定（内存 → 磁盘 → 端口/连接 → 网速）、条起点与宽度基准一致 → 视觉上形成隐式列 |
| 刻度一致 | 条分母 = 全表该列最大值（§3.4），跨卡可比 |
| 排序显式化 | 顶部分段控件 6 字段 + 方向切换，替代表头排序；这是卡片布局找异常的主路径 |
| 结论前置 | 「大户」spotlight 直接给出内存 / CPU / 进程 / 下载四个第一，不用扫全屏 |

明确**不做**：图标大屏、圆形仪表盘、动画图表——960×640 的工具窗要信息密度。

- 卡 hover：边框由 `tertiary` → `secondary`，不位移不阴影（保持平面语言）
- 点击卡片任意处 = 展开该卡（`grid-column: 1 / -1`），**同时只展开一张**；再点收起
- 排序段控件：点击字段即按该字段降序；再点同字段切升序，箭头 `▾ / ▴` 翻转
- **排序变化 ⇒ Top 12 重算**：切到「下载」后，前 12 张是下载前 12 名（这正是预期）；已点过「展开剩余」则保持全量显示，不自动折回
- 切排序 / 搜索时**自动收起已展开的卡**（否则那张卡可能掉出 Top 12，展开态凭空消失）
- 排序是**稳定排序**，同值时按家族名升序，避免刷新时卡片互相换位（1 s 网速刷新最容易抖）
- 搜索即时过滤（家族名，大小写不敏感）；搜索态显示**全部匹配项**并隐藏折叠门控；分母按匹配集合重算（§3.4）
- 「大户」spotlight 只在无搜索、无自定义排序时显示（避免与当前排序矛盾）
- 网速行数字 1 s 刷新即可；走势用 56 px 宽 sparkline，仅在展开卡里显示
- 折叠门控是一条**整行宽的低调条**（`background: secondary`、无边框、居中文字 + `⌄`），不是显眼的主按钮——它的角色是「还有更多」，不该抢走卡片的注意力

### 4.2 展开态（卡内下半区，整行宽）

展开后卡片变成「摘要 + 详情」两段，中间 1 px 分隔线：

1. **磁盘三层**（本体/缓存/数据，M8 现成按钮，按需触发）
2. **端口清单**（含对外暴露标注）
3. **进程 Top 3**（家族内最重的成员，提示可去「内存·应用」看全量）
4. **60 s 网速走势**（前端 ring buffer 60 点，复用 `Sparkline`；tab 切走清空，不落盘）

摘要段数字**不重复**详情段（例如端口数已在头部，详情只列具体端口）。

### 4.3 折叠门控（默认 Top 12 ↔ 展开全部）

```
默认（12 张）                                    点开后（48 张）
┌──────────────────────────────────┐            ┌──────────────────────────────────┐
│  …第 11、12 张卡…                │            │  …第 11、12 张卡…                │
├──────────────────────────────────┤            ├──────────────────────────────────┤
│     ⌄ 展开剩余 36 个             │            │  …第 13、14 张卡…（继续滚动）    │
└──────────────────────────────────┘            │  …                               │
                                                ├──────────────────────────────────┤
                                                │     ⌃ 收起，只看 Top 12          │
                                                └──────────────────────────────────┘
```

| 状态 | 触发 | 文案 | 说明 |
|---|---|---|---|
| 折叠（默认） | 进入 tab / 刷新 / 切排序（若此前未展开过） | `⌄ 展开剩余 36 个` | 剩余数 = 总数 − 12，**动态计算**，不是硬编码 |
| 展开全部 | 点门控 | `⌃ 收起，只看 Top 12` | 每张卡照常渲染，无分页、无虚拟滚动首期不做 |
| 搜索中 | 输入关键字 | 隐藏门控 | 搜索结果全量显示，标题行改「匹配 7 个」 |
| 切排序 | 点排序字段 | 保持当前折叠状态 | 若「已展开」则继续全量，避免用户每换一次排序就掉回 12 张 |
| 应用数 ≤ 12 | 系统干净时 | 隐藏门控 | 不足 12 个还显示「展开剩余 0 个」很傻 |

- **门控状态不持久化**：切走 tab 再回来回到「Top 12」，与「统计/端口 tab 每次进入重新读」的一致性原则相同；避免用户几个月后回来发现自己在滚 48 个应用，却不知道为什么
- 门控只是**渲染数量**开关，不是数据过滤：进程总数、合计网速、spotlight 始终按全部应用计算（§3.4 分母同理）

### 4.4 空值 / 降级态

```
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ ⚠ 网速不可读：nettop 不可用或解析失败（macOS 13+ 应自带）。卡片网速行保持空白，不估算。│
└──────────────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────┬─────────────────────────────────────────────────┐
│ ▸ Cursor                   54 进程  │ ▸ Xcode                              31 进程  │
│   188% CPU · 3 端口 ● · 33 连接     │   12% CPU · — 端口 · — 连接                  │
```

- 顶部状态条只在该域不可用时出现，正常时沉默
- 空值行**不画条**（缺失 ≠ 0 宽度）
- 空值只用三种文案：`—`（无口径/无数据）、`测量中…`、`采样中…`；**永远不出现 0 冒充缺失**
- 卡片内部不做骨架屏闪烁，只用文案（避免 1 s 刷新造成持续跳动）

## 5. 采集与生命周期

### 5.1 网速通道（新，实施时由「流式订阅」改为「1 s 轮询」）

```
前端 tab 可见 ──net_speed_set_active(true)──▶ NetSpeedState.active = true
                                              │
                    每秒一次（仅在 active 时）  ▼
        spawn: nettop -P -x -l 1 -t external -J bytes_in,bytes_out
                    │  stdout（一次性）
                    ▼
   解析：name.pid, bytes_in, bytes_out（CSV / 空格对齐两种形态都吃）
                    │
   与上一轮累计值差分 ÷ 实际间隔 → HashMap<pid, Speed>
                    │
   emit net://speed { at, perPid, status, note, intervalMs }
                    │
   前端：家族 pid 集合 → 求和 → 卡片「网速」行 + 展开卡 sparkline
```

**为什么改掉原设计（实测结论）**：

| 方式 | 实测 | 结论 |
|---|---|---|
| 流式 `-L 0 -s 1` | 重定向到管道/文件时是 **4 KB 块缓冲**，4.5 s 才吐出第一批 | 要行缓冲必须 `script` 包一层 pty，为一个读数引入 pty 包装不值 |
| 一次性 `-l 1` | 10 次共 0.145 s → **14.5 ms/次** | ✅ 采用：随起随灭，没有「子进程跑飞了要 kill」的生命周期问题 |

- **单实例**：循环本身串行，不可能并发 spawn
- **门控**：`active=false` 时连子进程都不 spawn（`pgrep nettop` 为空），常驻开销 0
- **基线重置**：切走 tab / 失败恢复后清空上一轮累计值——否则第一次差分算的是「离开这段时间的平均速率」，语义上已不是「当前网速」
- **失败降级**：spawn 失败 / 连续 3 个空样本 → `status: "unavailable"` + note；之后 5 s 退避重试
- **退出清理**：一次性子进程没有残留风险（这也是轮询相对流式的额外好处）

### 5.2 批量 bundle 测量（新，复用 M8 du 预算）

- 命令：`app_bundles(items: [{family, exe}], force?) -> HashMap<String, BundleSize>`
- 8 路并行 du + 单应用 4 s deadline（沿用 `du_budget`）；**按 bundle 路径去重**（Chrome 42 个帮助进程指向同一个 `.app`）
- 缓存挂在 `AppDiskState.bundles`（TTL 30 min）；新出现的家族会补测，不会因为「缓存里没有」一直空着
- 只在 tab 首次进入时请求一次；刷新按钮 `force = true` 重测

### 5.3 端口

同 M9：tab 可见 → `initPorts()`（有快照只读，无则扫一轮），**不调 setActive**，不挂 30 s 定时轮。

## 7. 假事实规避清单

| 陷阱 | 规避 |
|---|---|
| nettop 缺失/解析失败时显示 0 KB/s | 顶部状态条 + 卡内「—」；状态 `unavailable` 带原因 |
| 首轮差分前显示 0 | 「采样中…」 |
| 把回环流量算进「网速」 | `-t external`，tooltip 明示 localhost 不计 |
| 按进程名匹配家族（名字被截断） | 只按 pid 匹配 |
| 卡内「磁盘」被当成「总占用」 | 行尾 `?` tooltip 明写「仅 .app 本体；缓存/数据在展开区按需测量」 |
| 网速当成累计流量 | 只给 B/s；tooltip 说明是 1 s 差分速率 |
| 卡片里出现两个「内存」数字不一致 | 与内存·应用 tab 共用 `totalOf(family)` 同一函数 |
| 比例条被读成「占系统总量的百分比」 | 分母 = 全部应用（搜索时为匹配集合）的最大值；不显示百分数，tooltip 写明「条长 = 相对最大应用」 |
| 进程徽标数与「内存·应用」tab 不一致 | 同源 `FamilyMem.processCount`，同一家族口径，不加本地过滤 |
| 「大户」spotlight 被当成健康建议 | 只做排序导航，不带「建议结束」措辞 |
| 1 s 刷新导致卡片上下跳动 | 卡片固定高、数字区固定宽度（等宽字体 + 预留位）；排序用稳定排序 |
| **Top 12 被读成「我只有 12 个应用」** | 顶部文案固定为「显示 12 / 48」，门控条写「展开剩余 36 个」，两处都不省略总数 |
| **展开剩余时条长缩水，像数据变了** | 分母只受「搜索」影响，不受「渲染几张」影响（§3.4） |
| **搜了却搜不到（被 Top 12 截断）** | 搜索态全量匹配、隐藏门控、标题改「匹配 N 个」 |
| **切排序后展开的卡凭空消失** | 切排序/搜索时自动收起已展开卡 |
| 标题数字与卡片不符（剩余数硬编码） | 剩余数 = `总家族数 − 当前渲染数` 动态计算；≤12 个应用时隐藏门控 |

## 8. 验收清单

1. 启动进入「应用资源」tab：**进程 / CPU / 内存 / 端口 / 连接立即有数**（网速 1–2 s、磁盘 ≤1 s 后填充）
2. **默认只渲染 12 张卡**，顶部写「显示 12 / 48」，底部一条「展开剩余 36 个」；点开后 48 张全出，门控变「收起，只看 Top 12」
3. 网格为双列、卡片同高、指标行序一致；960×640 下不横向溢出、不出现半张卡
4. 排序切「下载」→ 前 12 张变成下载前 12 名（Top 12 随排序重算）；已展开状态下切排序不回折
5. 排序切「进程」→ 进程最多的家族在首位（与 `prune app` / 内存·应用对齐）
6. 比例条：默认内存降序时首位内存条为满宽、末位接近不可见；**展开剩余后条长不变**（分母仍是 48 个的最大值）；搜索后按匹配集合重算
7. 搜索 `cur`：只显示 Cursor 家族、门控隐藏、标题「匹配 1 个」、spotlight 隐藏；清空恢复 12 张 + 门控
8. 点击卡片跨两列展开，同时只有一张展开；展开后端口清单、进程 Top 3、磁盘三层、60 s 走势齐全；切排序时自动收起
9. 应用数 ≤12 的环境（或过滤后 ≤12）不显示门控
10. 切走 tab：`nettop` 子进程被 kill（`pgrep nettop` 为空），CPU 回落；切回重新采样且回到 Top 12、sparkline 从空开始
11. nettop 换成 `/bin/false`（故障注入）：卡内网速行「—」+ 顶部说明条，**不崩、不显示 0、不画条**
12. 1 s 刷新观察 60 s：卡片高度不变、数字不换行、卡片不互相换位
13. `npx tsc --noEmit` 0 错误、`cargo test --workspace` 全绿、浏览器 fixture 走查 + `pnpm tauri dev` 真机
14. 若走查判定扫视效率明显低于表格：`variant="compact"` 单列紧凑模式可用（逃生舱，不进默认）

## 9. 工作量与风险

约 **2.1 人天**：A0 0.8（解析 + 子进程生命周期 + 门控最费） / A1 0.2 / A2 1.0（卡片双 variant + 网格 + 展开 + 排序控件 + 折叠门控） / A3 0.1。

| 风险 | 影响 | 处置 |
|---|---|---|
| 卡片失去列对齐 | 跨应用扫视变弱 | §4.0 四条补偿；默认内存降序 + Top 12 + spotlight 兜住「找第一」；预留 compact 逃生舱 |
| **Top 12 把「不常看但重要的应用」藏起来**（比如磁盘 30 GB 但内存只有 200 MB 的归档工具） | 用户以为没有它 | 切排序即重算 Top 12（切「磁盘」就露出来）+ 搜索全量匹配；顶部常显总数，门控明示剩余数量 |
| 每屏可见 4 卡、Top 12 需滚 2 屏 | 仍有滚动 | 可接受：比 8 屏砍掉 75%；折叠门控不持久化，避免长期被迫滚 48 个 |
| nettop 无格式契约（私有 CLI） | 解析可能随系统版本变化 | 防御式解析 + 失败降级 + 单测覆盖；不改用私有框架 |
| 1 s 间隔常驻成本 | 耗电 | 只在 tab 可见时跑；实测单轮 22 ms，实施时用活动监视器复核，超 3% 退到 2 s |
| 大量应用 bundle du | 首屏慢 | 8 路并行 + 4 s deadline + TTL 30 min；**默认只渲染 12 张但测量仍覆盖全部**（切排序立刻有数），超时显示「≥ 下界」 |
| M8 入口受影响 | 回归 | `AppResourceCard` 保留 `detail` 用法，M8 展开逻辑不动；改完跑 M8 走查项 |
| 家族成员很多（Chrome 40+） | 求和慢 | pid→speed 是 HashMap 查找，O(进程数)，可忽略 |
